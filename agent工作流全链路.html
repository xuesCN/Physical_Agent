1 Chat 流式链路 · 分阶段拆解

入口文件 api/server.py → agent/chat_runtime.py（ChatRuntime.respond_stream）。这是最主力的「档位1：聊天起草→人批」工作流。

阶段 A｜入口与上下文组装（①–④）

  • ①② 前端 POST /api/chat/stream，FastAPI 用 StreamingResponse(media_type="text/event-stream") 打开 SSE，注册一个带 stream_id + threading.Event 的流状态（供中断），再调 respond_stream(message, cancel_check, transport_observer)。
  • ③ append_chat_message("user", message) 先把用户消息落库；然后一次性读齐 read_capabilities / read_world / read_feedback / read_chat / read_memory，并做一次确定性关键词检索 _retrieved_context(message)。
  • ④ build_context(purpose="proposal")（agent/context_builder.py）按 ContextBudget 把 SAFETY/world/capabilities/feedback/memory/chat 逐块裁进预算：chat 超 24 条触发滚动摘要、只留最近 12 条；memory 按 (importance, created_at) 排序取 top-20。产出 ContextBundle{system, messages, max_tokens, temperature}。

阶段 B｜OpenAI SDK 流式编排（⑤–⑧）· 本文重点

⑤ ChatRuntime._stream_chat_decision_with_llm 调 client.stream_structured_json(bundle.messages, schema=CHAT_RESPONSE_SCHEMA, schema_name="physical_agent_chat_response", temperature, max_tokens, metadata={"physical_agent_surface":"chat_stream"}, transport_observer)。注意：流式走的是 json_object 模式而非 json_schema——因为流式无法在开流后再切格式，所以先把 schema 以文字指令塞进 system（_messages_with_json_mode_instruction），格式只用宽松的 {"type":"json_object"}，正确性靠流末本地 jsonschema 兜。

⑥ SDK 内部 _stream_chat_completions_text 组 payload：model / messages / temperature / max_tokens / stream=True / response_format，再 _apply_chat_reasoning 把 reasoning_extra_body 注入 extra_body（默认开深度思考），然后 self._client.chat.completions.create(**payload)——这就是真正的 openai-python SDK 调用。

⑦⑧ 逐块迭代 for chunk in stream：_chat_delta_contents 抽 choices[].delta.content，包成 StreamChunk(kind="message"|"thought", text) yield 回 ChatRuntime。ChatRuntime 一边把 message 块喂给 _IncrementalJsonReply（一个手写的增量 JSON 字符串解码器，只解 top-level reply 字段、不缓冲尾巴），一边把解出的自然语言增量通过 SSE {type:"delta"} 推给前端；thought 块走 {type:"thought"}。transport_observer 把底层流的 close() 暴露出去，前端断连/abort 时能真正掐断 HTTP 流。

降级链（只在开流前、未吐字节时允许）：stream_structured_json 先试 json_object；若报「response_format 不支持」且尚未 yield 任何 chunk，回退到无 response_format 的纯文本流。_apply_chat_reasoning 若报「reasoning 不支持」且未吐字节，_retry_chat_stream_without_reasoning 去掉 extra_body 重开。一旦已经吐过字节就绝不降级——避免把两个互相竞争的决策拼接起来。

阶段 C｜结构化解析与双重校验（⑨）

  • ⑨ 流结束后，parse_structured_json_text("".join(raw_parts), schema=CHAT_RESPONSE_SCHEMA) = json.loads + jsonschema.validate 本地强校验（schema 要求 reply/intent/steps/actions/memory，additionalProperties:false，intent 枚举 chat/inspect/act/remember）。
  • 再做一致性断言：流式增量拼出的 reply 必须等于校验后 response["reply"]——否则抛错。这保证「给人看的增量」和「落库的权威决策」是同一份，不会串。
  • yield {"type":"decision", "response":...} 交回 respond_stream。

阶段 D｜信任编译 PlanCompiler（⑩⑪）· 信任边界

_prepare_chat_turn 把原始 decision 归一化后调 compile_agent_output(actions, status="draft", decision="propose", lifecycle="draft", capabilities, safety_rules)（application/plan_compiler.py）。编译器不信模型自称，为每个 action 重建一张任务 DAG：

  • approval 任务（owner=human）：是否需要审批由 _approval_required_from_facts 用可信 capability/SAFETY 事实决定，覆盖模型 metadata 里自称的 approval。
  • safety_gate 任务（owner=watch，mandatory=True，policy_source="SAFETY.md"，checks=safety_check_specs()）：模型无法创建/完成/绕过它；依赖上游 physical_action + approval。
  • physical_action 任务（owner=watch，依赖对应 gate）。
  • verification 任务（owner=watch，mandatory=False）：仅当 action 带 metadata.expected 时生成，用于执行后确定性比对。

产出 AgentOutput（含 tasks + actions）。chat 链路 lifecycle="draft"，物理任务状态是 not_scheduled——只画图不排队。

阶段 E｜落库与收尾（⑫⑬）

  • ⑫ _finish_stream_reply：append_chat_message("assistant", reply) → write_chat（内部 compact_chat_messages 顺带触发压缩），并把 AgentOutput/reasoning_summary 一并持久化。
  • ⑬ SSE 收尾事件 {type:"done", ...agent_output}；前端拿到 draft 提案渲染成任务图卡片。到这里没有任何物理动作发生。
  • 异常/中断：_ChatStreamAborted→{type:"aborted"}、GeneratorExit（前端断连）→落一条 cancelled、其它异常→{type:"error"}，每种都保证 chat 状态被一致落库。

2 OpenAI SDK 编排层细节

全部集中在 llm/openai_compatible.py 的 OpenAICompatibleClient（包 openai.OpenAI(api_key, base_url, timeout)）。它对上层暴露四类调用，屏蔽两种 API 形态和各种 provider 差异。

两种 API 形态（一套代码双通道）

api_mode 可选 chat_completions（默认）或 responses。前者走 client.chat.completions.create，reasoning 经 extra_body；后者走 client.responses.create（system→instructions、messages→input、max_output_tokens），reasoning 经 reasoning:{effort,summary}，流式事件是 response.output_text.delta（message）/ response.reasoning_summary_text.delta（thought）。上层 stream_chat_text 按 mode 分派，返回统一的 StreamChunk，调用方无感。

四个对外方法

方法用途格式策略
chat()非流式取文本直接返回 choices[0].message.content
structured_json()非流式取结构化（run_task/planner 用）strict json_schema → 400 则退 json_object → 再退纯文本 → 本地 jsonschema 校验
stream_chat_text()流式文本逐块 StreamChunk
stream_structured_json()流式结构化（chat 用）json_object → 未吐字节则退纯文本；schema 塞进 system 指令

三条降级链 + reasoning 回退

  • 格式降级（非流式）：structured_json 遇 is_bad_request → json_object；再遇 _is_response_format_unsupported_error → 无 response_format 纯文本。三次都本地校验，保证不同 provider 都能落地。
  • 格式降级（流式）：只在 yielded==False 时允许，防止拼接两个决策。
  • reasoning 回退：_is_reasoning_unsupported_error 命中（bad_request/stream_error 且含 reasoning/thinking/extra_body 等词）→ _reasoning_fallback_payload 去掉 reasoning 键重试，并打 reasoning_fallback 标记。

增量 JSON 解码器 _IncrementalJsonReply

流式下模型吐的是 {"reply":"你好...","intent":...} 的字节流，但用户要实时看到「你好...」。这个手写解码器定位到 top-level reply 字符串的起点后，逐字符解转义（含 \\uXXXX 和代理对），只吐 reply 的内容增量、遇到闭合引号即 complete，不缓冲整个 JSON 尾巴。这样「首字延迟」只取决于模型何时开始写 reply 字段。

横切能力：①错误归一化 _to_compatible_error 把 SDK 异常分类成 rate_limit/timeout/connection/bad_request/status；②Key 脱敏 _sanitize_error 把 api_key、Bearer xxx、api_key=xxx 全替换成 <redacted> 再抛；③本地 trace _write_llm_trace 把每次调用（messages/response/usage/latency/error）落到 workspace/llm-trace/YYYYMMDD.jsonl（PA_LLM_TRACE 可关）；④base_url 校验 拒绝以 /chat/completions 结尾的错误配置。

3 执行侧 · watch tick（⑮–⑱）

watch/runtime.py。watch 是唯一执行者，与认知侧完全解耦，靠 SQLite 黑板通信。它不被 chat 请求触发，而是独立循环 run_forever → tick → step → _step_once。

  • 租约先行：每个 _step_once 先 _renew_watch_lease()，租约丢了直接拒绝处理（保证单写者）。心跳所有 driver、更新看门狗。
  • ⑮ 原子领取：claim_next_ready_action(claim_owner, blocked_robot_ids) 在 SQLite BEGIN IMMEDIATE 事务里「选一个 ready + 标记 claimed」一步完成，杜绝两个执行者抢同一个（TOCTOU）。心跳不健康/被看门狗停的 robot 会被排除。
  • ⑯ 过闸：构造 SafetyGate(robots, safety_rules, completed_ids, executed_ids, default_timeout) 调 gate.validate(action) 跑 10 项检查（action_id 唯一→依赖完成→robot 已知→robot 就绪→capability 已知→自主档位→审批满足→参数 schema→数值 bounds→超时预算）。_record_safety_gate_decision 把每项 check 写进 feedback。deny → 动作置 cancelled + 记 result + expectation 标 skipped，continue。
  • ⑰ 执行：唯一一次 loaded.driver.execute(action)，包在 _call_with_timeout(..., timeout_s) 里。超时→DriverCallTimeout→先 _halt_robot_after_timeout（宁停不乱动），再记失败；transport 断连/其它异常各有分支，都置 cancelled。
  • ⑱ 回灌：成功则 _finalize_claimed_action(completed)；_record_action_result 追加 feedback；带 expected 的做确定性比对（不用 LLM 当裁判）；update_world 刷新世界快照，回灌下一轮上下文，形成闭环（F4）。

4 其他入口 · 编排对比

五入口共用同一条「不可信→编译→落库→执行」管线，差别只在认知侧怎么产出 action 意图。执行侧（watch/SafetyGate/driver）完全相同。

关键收敛点：

  • tool_loop 白名单：ALLOWED_TOOL_NAMES 只有 submit_task / propose_action / get_state——工具只能提案，碰不到 driver；max_steps 限制轮数防死循环。
  • planner 可切：create_planner 按 config.agent.planner（yaml）选 LLM 或 rule_based——不是所有决策都烧 LLM。
  • PlanCompiler 是唯一信任边界：chat 走 lifecycle="draft"，run_task/tool_loop/submit 走 "submitted"，但都经 compile_agent_output 注入同一套 watch-owned safety_gate 任务。ProposalService 是唯一 append_pending_actions 的地方。
面试怎么讲（概念优先，项目当证据）：面试官没看过你的代码，别一上来堆项目专名。先讲可迁移的模式，最后一句才落到实现。
  • ① 模式（一句话）：把「想」和「做」分离——LLM 只产出结构化的动作意图，绝不直接执行；意图先被可信层重建、排队，再由一个独立的单写执行器逐个消费、执行前强制校验才动手，结果回灌下一轮。
  • ② 编排怎么做：强制结构化输出，用降级链（strict JSON schema → json mode → 纯文本 + 本地校验）扛住不同 provider；流式加「吐字节后不再降级」的纪律，防止拼接两个决策；深度思考默认开、provider 不支持自动回退。
  • ③ 为什么这么排：物理动作不可逆、没有 Ctrl+Z，所以把信任边界收敛到「一个编译器 + 一道执行前闸门」，即使模型被 prompt 注入也只能提议危险动作，越不过校验。
  • ④ 落地一句（才上专名）：「在我的物理 agent 里，这四层是 ChatRuntime → PlanCompiler → SQLite 黑板 → watch + SafetyGate（执行前 10 项检查）；无论流式 chat、非流式 planner 还是 tool-calling，都汇到 PlanCompiler 这一个信任边界。」
要点：可迁移的模式讲给任何面试官听，项目专名只留一句当证据——深挖的顺着追问再展开，不深挖的也听懂了。
